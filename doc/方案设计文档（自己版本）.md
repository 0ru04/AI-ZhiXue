# 《AI智学》方案设计文档

> 文档状态：MVP 技术方案  
> 资料检索日期：2026-10-17  
> 目标：微信小程序首发、中国大陆正式上线；前端 Taro + React + TypeScript，后端 Python + FastAPI，模型 DeepSeek `deepseek-flash`。  
> 说明：模型标识、价格、平台审核规则和 SDK 兼容性可能变化；上线前须复核官方文档。本文中的产品默认值是可供 MVP 实施的建议，不替代产品、合规或安全审查。

---

## 1. 产品范围与阶段目标

### 1.1 产品定位

《AI智学》将用户提供的文本或主题转换为短小的自测题，并通过即时反馈、讲解和答题复盘帮助用户学习。MVP 优先验证“输入内容—生成题目—逐题作答—查看报告”的完整闭环，不提前建设账户、长期知识库或商业化系统。

### 1.2 MVP 核心能力

1. 用户输入一句话、一段文本或一个学习主题。
2. 后端调用 DeepSeek 生成 3–5 道单选、多选或判断题。
3. 用户逐题作答，提交后立即看到正确答案、对错和讲解。
4. 全部题目完成后，生成答题统计、知识总结和复盘建议。

### 1.3 MVP 范围外

- 用户注册、登录、跨设备同步、历史答题后台和个人知识树。
- PDF/Word 解析、网页抓取、私有资料库和 RAG。
- 图片/音频题目、多人对战、排行榜、支付和 VIP。
- 高风险领域的专业考试、诊断或决策用途；MVP 输出不应被描述为权威教材或正式测评结果。

### 1.4 分阶段扩展

| 阶段 | 目标能力 | 建议前置条件 |
|---|---|---|
| MVP | 文本/主题输入、题目生成、逐题反馈、报告 | 先验证题目质量和核心留存 |
| 输入源扩展 | 文本抓取、PDF/Word 解析 | 先定义文件大小、格式、版权和安全限制 |
| 用户与历史 | 登录、云端答题历史、知识树 | 明确账号体系、数据保留和隐私说明 |
| 私有知识库 | 向量检索/RAG | 有稳定资料解析、切分、引用和评测方案后再建设 |
| 多模态/商业化 | 图片/语音、PK、排行榜、付费 | 单独评估平台能力、内容审核和支付政策 |

## 2. 技术选型

### 2.1 前端小程序候选

比较的主要候选为微信原生小程序、Taro 和 uni-app。评价采用定性判断，不把框架宣传中的跨端能力等同于项目实际节省的工作量。

| 维度 | 微信原生 + TypeScript | Taro + React + TypeScript | uni-app + Vue 3 + TypeScript |
|---|---|---|---|
| 学习与开发成本 | 要学习 WXML、WXSS、微信组件和 API；只做微信时概念直接 | 需掌握 React、Taro 编译约定及微信差异；已熟悉 React/TS 时成本较低 | Vue 语法上手较快；需理解 uni-app API、条件编译和运行时约定 |
| 微信适配程度 | 最高，直接使用微信原生能力和组件 | 支持编译到微信小程序；平台专有能力仍需核实和编写差异代码 | 支持微信小程序；标准 API 映射到各端运行时，专有能力仍需按平台测试 |
| 多端扩展能力 | 较低；增加平台通常要重写页面层 | 高，可面向多个小程序、H5 等目标，但不是所有 API/组件都能无差异复用 | 高，官方支持多个小程序、Web 和 App 等目标 |
| 生态成熟度 | 微信文档、开发者工具和原生组件生态直接 | 社区和跨端开发生态成熟；依赖 Taro 版本及目标端适配 | DCloud 文档、插件市场和 Vue 生态丰富 |
| 组件/插件可用性 | 微信原生组件适配直接，跨平台组件少 | React/Taro 组件较多；依赖原生微信组件或特殊 API 时需做兼容验证 | Vue/uni-app 插件多；插件支持的平台和质量需逐个核验 |
| 性能与调试 | 原生链路短，开发者工具调试直接 | 增加编译层；需同时检查 Taro 编译产物和微信端行为 | 增加编译器/runtime 映射层；需在目标平台真机验证 |
| 单人开发友好度 | 微信限定、需求简单时非常直接 | 熟悉 React 时良好；框架和跨端边界需维护 | 熟悉 Vue 时良好；HBuilderX/CLI 及平台差异需要纳入工作流 |
| 本项目 MVP 适配度 | 很高，适用于确定只做微信的情况 | **高，符合已确认的 React/TS 技术方向，并保留多端选项** | 中高；若开发者更熟悉 Vue 或多端近期成为硬需求，可优先考虑 |

#### 推荐结论

采用 **Taro + React + TypeScript**。

这是结合项目“微信首发、未来可能扩展”和用户已经确认的 React/TypeScript 方向所作的推荐。Taro 提供多端编译入口，但 MVP 仍以微信小程序为唯一验收平台；页面、组件和第三方插件不能因为可以编译就视为已跨端兼容。

#### 推荐理由

1. React + TypeScript 适合将首页、答题页、报告页拆为可复用组件，并以 DTO 类型明确前后端契约。
2. Taro 官方支持微信小程序及其他小程序/H5 等目标；未来扩展时可以优先复用业务逻辑和部分 UI。
3. 通过开发初期就在微信开发者工具与真机上验证，可以尽早发现组件、生命周期、网络 API 和样式差异。

#### 不推荐其他方案作为当前主选的原因

- **微信原生**：平台兼容性最好，但与已确认的 React/TypeScript 开发方向不一致；后续增加其他平台时，页面层迁移工作较多。若产品确定长期只支持微信，可重新评估原生方案。
- **uni-app**：跨端能力和 Vue 生态是优势，但需要维护另一套 Vue/uni-app 工作流；当前开发方向已确定为 React，因此不作为主选。若团队转向 Vue 或多端交付成为首发目标，应重新比较。

#### 前端备选策略

- 已确认以 Taro 为主，微信原生 API 可通过 Taro 能力或有边界的微信专属代码接入。
- 当某个页面或插件依赖大量微信专有能力、跨端抽象造成明显性能/调试问题时，优先把差异封装在 `platform/wechat` 或适配层，而不是在业务页面散落条件编译。
- 若后续首版变成多端同步发布，应先建立目标平台矩阵和真机回归清单，再评估 Taro 与 uni-app 的实际适配成本。

### 2.2 后端语言与框架候选

| 维度 | Python + FastAPI | Node.js + Fastify | Java + Spring Boot |
|---|---|---|---|
| 学习与开发成本 | Python 语法清晰；FastAPI 支持类型提示、请求校验和自动 API 文档 | 若熟悉前端 TypeScript/JavaScript，语言切换少；需自行明确模块边界 | 生态和工程规范成熟；MVP 的依赖注入、配置和工程结构相对更重 |
| 与小程序适配 | 通过 HTTPS JSON API 解耦，语言不影响小程序调用 | 同样通过标准 HTTP API 解耦；TS 类型可在前后端共享/生成 | 同样通过标准 HTTP API 解耦 |
| 多端扩展 | API 契约不绑定客户端；可服务多种客户端 | 同左 | 同左 |
| 生态与 AI 接入 | Python 的数据/AI 工具丰富；DeepSeek 官方给出 OpenAI 兼容 Python SDK 接入示例 | Web API 生态成熟；Fastify 有 TypeScript、JSON Schema 文档 | 企业级 Web 服务和中间件生态成熟 |
| 调试/开发体验 | FastAPI 提供交互式 API 文档；类型检查建议使用 Pydantic 与静态检查工具 | Fastify 支持路由 schema 和 TS；插件类型质量需按依赖验证 | IDE、诊断和成熟工程工具支持较好 |
| 单人开发友好度 | API 数量少、接入模型直接；需要单独维护 Python 环境与锁文件 | 与 React/Taro 共享语言有优势 | 更适合已有 Java 经验或组织级后台标准的项目 |
| 本项目 MVP 适配度 | **高，满足用户选择；模型接入和请求/响应校验清晰** | 高，若优先考虑全栈 TS 可作为替代 | 中，适合已有 Java 基础或后续明确发展为企业后台 |

#### 后端推荐结论

采用 **Python + FastAPI**，依赖使用锁文件固定；使用 Pydantic 定义请求/响应结构，用 `httpx` 或官方兼容的 OpenAI Python SDK 调用模型。开发环境版本以 FastAPI 及其依赖当前支持的 Python 稳定版本为准，首次搭建时写入项目配置和锁文件，不在文档中虚构一个长期不变的精确版本号。

#### 推荐理由

1. 用户已确认 Python + FastAPI，适合以少量 HTTP 接口快速形成 MVP。
2. DeepSeek 官方提供 OpenAI 兼容接口和 Python 示例；调用层可以使用兼容 SDK，并将模型配置集中管理。
3. FastAPI 的请求校验和自动生成 OpenAPI 文档便于前后端并行开发、联调和测试。

#### 其他方案不作为当前主选的原因

- **Node.js + Fastify**：如果用户更偏好前后端同为 TypeScript，这是最直接的替代方向；本项目已经确定 Python/FastAPI，因此不同时维护两个服务端技术栈。
- **Java + Spring Boot**：若未来出现企业集成、团队统一 Java 标准或复杂后台需求，可重新评估；对当前单人 MVP 来说并非必要起点。

### 2.3 已确认的 MVP 技术栈

- 前端：Taro + React + TypeScript，主要目标微信小程序。
- 后端：Python + FastAPI，提供版本化 JSON/HTTPS API。
- 模型：DeepSeek `deepseek-flash`。
- 模型访问：后端调用 `https://api.deepseek.com`；API Key 只存服务端环境变量/密钥配置，不进入小程序代码、构建产物或日志。
- 持久化：MVP 不建设正式数据库；前端临时保存当前答题状态，服务端无状态处理请求。
- 部署：中国大陆可访问的服务端与 HTTPS 域名；域名按微信要求配置服务器域名并完成 ICP 备案。具体云服务商和规格待部署前依据预算、备案主体和服务范围另行选择。

## 3. 系统总体架构

### 3.1 架构目标

1. 前后端可以并行开发：API schema 先行，前端可用 Mock 数据开发。
2. AI 输出必须经过结构解析、字段校验和业务校验；不能让 UI 依赖自然语言文本解析。
3. 输入源、用户系统、历史记录和 RAG 可在边界稳定后扩展，不把 MVP 做成过度抽象的平台。
4. 所有模型凭证仅保留在服务端；失败通过明确的 HTTP 状态码和错误码反馈。

### 3.2 逻辑架构

```text
微信用户
   │
   ▼
Taro 小程序（首页 / 答题 / 报告）
   │  HTTPS + JSON，仅请求已配置业务域名
   ▼
FastAPI（API 路由 / 请求校验 / 业务服务）
   │
   ├── QuizService / ReportService
   ├── Prompt 与 Pydantic 输出校验
   └── DeepSeek Client（服务端密钥）
           │ HTTPS
           ▼
       DeepSeek API
```

MVP 不放置数据库。题目和答题记录由客户端暂存并随报告请求提交；后端只在处理请求期间使用数据，不提供历史查询。该方案适用于低风险自学闭环，不提供防作弊、权威考试或长期审计能力。

### 3.3 核心模块拆分

#### 前端模块

1. **页面与路由**：首页、答题页、报告页，负责页面状态和跳转。
2. **输入模块**：主题/文本输入、字符提示、题型和题量选择、前置校验。
3. **答题模块**：题目渲染、单选/多选/判断交互、进度、提交和即时讲解。
4. **报告模块**：总分、正确率、知识点表现、薄弱项及复盘建议展示。
5. **API Client**：统一 base URL、超时、请求 ID、响应解析和错误映射。
6. **领域类型**：Quiz、Question、AnswerRecord、Report 和 API DTO。
7. **本地会话状态**：当前 quiz、逐题答案、报告缓存；不在 MVP 做账号同步。

#### 后端模块

1. **API 层**：健康检查、题目生成、报告生成；校验输入并统一响应。
2. **Schema 层**：Pydantic 请求/响应对象及 AI JSON 输出对象。
3. **Service 层**：题目生成协调、报告统计计算、重试策略和业务错误。
4. **LLM 层**：DeepSeek HTTP/SDK 客户端、超时、模型名和密钥配置。
5. **Prompt 层**：题目生成 Prompt、报告 Prompt、版本标记和安全约束。
6. **异常与日志层**：错误码映射、requestId 关联、脱敏日志、健康探针。
7. **测试层**：schema 单测、Prompt 结构测试、API 集成测试和模型离线样例评测。

### 3.4 数据流

#### 流程一：用户输入并生成题目

1. 用户在首页填写主题或学习文本，选择 3–5 题和允许题型。
2. Taro 前端校验必填内容、长度和题量，展示加载状态。
3. 前端调用 `POST /api/v1/quizzes`。
4. FastAPI 校验请求并构造结构化 Prompt，明确将用户内容视为资料而不是系统指令。
5. 后端使用 DeepSeek JSON Output 请求模型；API Key 仅由服务端读取。
6. 后端解析 JSON，并校验题目数量、题型、选项 ID、答案引用和解释字段。
7. 校验成功后返回 Quiz；校验或模型调用失败时返回有明确错误码的失败响应，不返回伪造的成功结果。
8. 前端将 quiz 临时保存在页面状态/本地存储中，进入逐题答题页。

#### 流程二：用户答题

1. 前端一次显示一题，并按题型维护选中项。
2. 用户提交本题后，前端按题目答案字段比较所选项，显示正确/错误、正确答案和讲解。
3. 用户可继续下一题；前端记录每题选择和提交时间。
4. 完成全部题目后，前端将题目快照和答题记录发给报告接口。

> 由于 MVP 不持久化题目且即时反馈由客户端完成，题目响应中包含正确答案。用户可以从客户端数据中看到答案；该设计不用于防作弊或正式考试。若未来需要可信评分，必须改为服务端保存题目/答案并由服务端判分。

#### 流程三：生成报告

1. 前端提交 Quiz 快照及每题答案，不提交可信的 `isCorrect` 字段。
2. 后端校验题目和答案引用，重新计算正确数、正确率及知识点统计。
3. 后端将错题/薄弱知识点摘要发送给 DeepSeek，生成简短的知识总结和复盘建议。
4. 后端校验模型报告结构，组合服务端计算的统计结果和模型建议。
5. 成功返回报告，前端展示结果并允许重试练习。
6. 若模型调用失败，返回明确错误；前端保留答案记录，允许用户重试生成报告。

### 4.2 分层职责

| 层 | 职责 | 不应承担 |
|---|---|---|
| 页面层 | 组织页面状态、加载/错误/空态、页面跳转 | 直接拼接模型 Prompt 或散落调用请求 |
| 组件层 | 题目、选项、进度和错误提示等可复用 UI | 依赖完整全局 quiz 对象 |
| 状态/领域层 | 当前 Quiz、AnswerRecord、答题进度和派生统计 | 保存 API Key 或当作可信服务器数据 |
| 服务层 | 封装 API 路径、DTO、请求超时和错误映射 | 把后端错误吞掉或自动伪造成功数据 |
| 平台适配层 | Taro/微信专有 API 的集中封装 | 在各页面重复写平台判断 |

### 4.3 前后端交互原则

- 使用 REST/JSON，接口统一以 `/api/v1` 开始。
- API 类型应由共享契约/生成方式保持同步；若不能共享 Python 类型，则以 OpenAPI 为契约并在前端生成/校验类型。
- 客户端不含 DeepSeek 密钥、服务商密钥、微信 AppSecret 或内部服务地址。
- 所有模型调用失败必须提供可操作的错误提示；不得把失败静默替换成空题或假报告。
- 开发时可在开发者工具临时跳过域名校验，但正式联调必须使用 HTTPS 备案域名并关闭跳过校验。

### 5.2 后端分层职责

#### API 层

1. 声明 HTTP 方法、路径和 Pydantic 输入输出模型。
2. 校验请求字段、范围、长度及题目/答案关联。
3. 设置 requestId、HTTP 状态码和统一错误封装。
4. 调用 Service，不直接实现 Prompt 或模型解析。
5. 通过 `/health` 提供最小健康检查，不泄露密钥和内部配置。

#### Service 层

1. 实现题目生成和报告生成的业务流程。
2. 调用 LLM 层并检查模型业务约束。
3. 由服务端计算正确数、正确率和知识点统计，不信任客户端提交的统计字段。
4. 将可预期失败映射为领域错误；遇到未知错误要记录并返回明确的服务端错误。
5. MVP 不写数据库；只在单次请求中处理输入，避免全局可变数据。

#### LLM 层

1. 通过配置读取 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、模型名和超时。
2. 使用 DeepSeek 官方支持的 OpenAI 兼容 API 格式；建议 Python SDK 的异步客户端，或使用 `httpx` 封装。
3. 设置 JSON Output、合理的最大输出 token 和请求超时。
4. 分类处理空 content、JSON 解析错误、字段不合规、限速、网络超时和供应商 5xx。
5. 默认只调用 `deepseek-flash`；不自动切换到更贵模型，避免不可预期费用。

#### Prompt 层

1. 用明确的 system 指令定义角色、输出结构、题量和题型。
2. 将用户输入作为引用资料，不允许它覆盖系统规则或要求泄露 Prompt。
3. 要求每题给出答案、解释、知识点和必要的选项，不输出 Markdown 围栏。
4. 报告 Prompt 仅总结后端提供的题目和答题情况；分数/正确率始终由后端计算。
5. Prompt 修改需更新版本号并使用回归样例评测。

### 5.3 模型输出校验流程

DeepSeek JSON Output 保证输出为合法 JSON 字符串的目标，不等于对业务 Schema 的强约束；官方同时提示偶尔可能返回空 content。因此必须按以下步骤处理：

1. 检查响应完成状态和 content 是否为空。
2. 解析 JSON；解析失败则记录脱敏错误上下文并返回 `AI_OUTPUT_INVALID`。
3. 使用 Pydantic 校验字段类型、枚举、长度、数量和选项引用。
4. 校验单选恰有一个正确项，多选至少一个正确项，判断题答案符合约定。
5. 校验题目数量为 3–5、题目 ID 唯一、选项 ID 唯一、正确答案引用存在。
6. 失败时仅允许一次受控修复重试（如实现），且不能无上限重试；重试仍失败就返回明确错误。

## 6. 大模型接入方案

### 6.1 DeepSeek 模型比较

按官方模型与价格页在 **2026-10-17** 检索到的信息整理。价格单位为人民币/百万 tokens；高峰、低峰时段以 DeepSeek 官方定义为准。

| 项目 | `deepseek-flash` | `deepseek-v4-pro` |
|---|---|---|
| 官方服务版本 | DeepSeek-V4.1-Flash-1017 | DeepSeek-V4-Pro-0813 |
| 当前推荐调用名 | `deepseek-flash`；旧 `deepseek-v4-flash` 等名称对应模型已下线，官方建议用新名称 | `deepseek-v4-pro` |
| JSON Output / Tool Calls | 支持 | 支持 |
| 图片输入 | 支持 | 不支持（以官方模型表为准） |
| 账户并发上限 | 2500 | 500 |
| 输入（缓存命中）价格 | 低峰 ¥0.02；高峰 ¥0.04 | 低峰 ¥0.15；高峰 ¥0.30 |
| 输入（缓存未命中）价格 | 低峰 ¥1；高峰 ¥2 | 低峰 ¥4.5；高峰 ¥9 |
| 输出价格 | 低峰 ¥4；高峰 ¥8 | 低峰 ¥13.5；高峰 ¥27 |

价格会变化，必须以 [DeepSeek 官方模型与价格页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/) 为准。官方资料未提供针对本项目中文题目生成的可比准确率基准，不能把模型名称直接等同于质量结论。

#### 已确认的模型选择

MVP 使用 **`deepseek-flash`**。理由是当前功能每次生成 3–5 道题，优先控制输出调用成本并快速验证闭环；两款模型均支持项目所需 JSON Output。知识准确性必须通过项目样例评测验证，而不是假设 Flash 或 Pro 的名称即可保证正确。

当 Flash 不能达到项目验收标准时，再使用相同题库和输入对 `deepseek-v4-pro` 做对照测试；若改模型，记录价格、质量和响应时间差异后再调整。MVP 不配置自动升级/降级模型路由。

### 6.2 接入方式

1. 后端服务以环境变量读取 `DEEPSEEK_API_KEY`，默认 base URL 为 `https://api.deepseek.com`。
2. 使用 DeepSeek 官方文档兼容的 OpenAI Chat Completions 格式，模型名设为 `deepseek-flash`。
3. 请求设置 `response_format: {"type": "json_object"}`；system/user Prompt 中包含 `json` 并提供目标 JSON 示例。
4. 选择足够的 `max_tokens` 防止结构化输出中途截断；不要将模型原始输出直接返回给前端。
5. 通过 Pydantic 验证 JSON 的业务结构；向前端只返回内部 DTO。
6. 记录耗时、模型标识、token 用量（如供应商返回）和错误类别；不得记录 API Key、完整敏感输入或不必要的个人信息。
7. 用户输入可能包含个人或敏感内容。上线前应告知用户内容会发送至模型服务，最小化收集，并按适用的微信平台及中国大陆法规要求完成隐私/生成式 AI 服务审查。

## 7. 后端 API 设计

### 7.1 通用约定

- Base Path：`/api/v1`
- Content-Type：`application/json; charset=utf-8`
- 仅通过 HTTPS 访问；API 不接受模型供应商凭证。
- 所有业务响应包含 `requestId`，便于用户反馈和服务端排查。
- `success` 表示本次处理确实完成；失败不以 HTTP 200 或空内容伪装成功。

成功响应：

```json
{
  "requestId": "req_01J...",
  "data": {},
  "error": null
}
```

错误响应：

```json
{
  "requestId": "req_01J...",
  "data": null,
  "error": {
    "code": "AI_PROVIDER_TIMEOUT",
    "message": "题目生成暂时超时，请稍后重试。",
    "retryable": true
  }
}
```

错误信息面向客户端，不返回堆栈、Prompt、密钥、上游原始响应或基础设施细节。

### 7.2 接口清单

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/v1/health` | 存活检查 |
| POST | `/api/v1/quizzes` | 基于文本/主题生成题目 |
| POST | `/api/v1/reports` | 根据题目快照和答题记录生成统计与复盘报告 |

### 7.3 健康检查

**接口路径：** `GET /api/v1/health`

成功响应：

```json
{
  "requestId": "req_01J...",
  "data": {
    "status": "ok"
  },
  "error": null
}
```

仅用于服务存活探测；不在此接口中返回环境变量、模型密钥或内部依赖详情。

### 7.4 生成题目

**接口路径：** `POST /api/v1/quizzes`

请求体：

```json
{
  "source": {
    "type": "text",
    "content": "光合作用是绿色植物利用光能，将二氧化碳和水转化为有机物并释放氧气的过程。"
  },
  "questionCount": 3,
  "questionTypes": ["single_choice", "multiple_choice", "true_false"]
}
```

字段约定：

- `source.type`：MVP 为 `text`，后续可增加 `topic`、`document` 等类型。
- `source.content`：必填；初始建议长度上限 5,000 个 Unicode 字符，超过时返回 `422`。该上限需结合模型上下文、成本和产品输入体验在实现前确认。
- `questionCount`：3–5，默认 5。
- `questionTypes`：至少包含一种；后端只接受已支持的枚举。

成功响应示例：

```json
{
  "requestId": "req_01J...",
  "data": {
    "quiz": {
      "quizId": "quiz_7d9c...",
      "createdAt": "2026-10-17T10:00:00Z",
      "sourceSummary": "光合作用的定义与原料、产物",
      "questions": [
        {
          "questionId": "q1",
          "type": "single_choice",
          "stem": "光合作用的主要能量来源是什么？",
          "options": [
            {"optionId": "A", "text": "光能"},
            {"optionId": "B", "text": "声能"},
            {"optionId": "C", "text": "核能"}
          ],
          "correctOptionIds": ["A"],
          "explanation": "绿色植物利用光能驱动光合作用。",
          "knowledgePoint": "光合作用的条件"
        }
      ]
    }
  },
  "error": null
}
```

响应中的答案字段用于当前自学闭环和即时反馈，不能视为保密数据或防作弊设计。

### 7.5 生成报告

**接口路径：** `POST /api/v1/reports`

请求体示例：

```json
{
  "quiz": {
    "quizId": "quiz_7d9c...",
    "sourceSummary": "光合作用的定义与原料、产物",
    "questions": [
      {
        "questionId": "q1",
        "type": "single_choice",
        "stem": "光合作用的主要能量来源是什么？",
        "options": [
          {"optionId": "A", "text": "光能"},
          {"optionId": "B", "text": "声能"},
          {"optionId": "C", "text": "核能"}
        ],
        "correctOptionIds": ["A"],
        "explanation": "绿色植物利用光能驱动光合作用。",
        "knowledgePoint": "光合作用的条件"
      }
    ]
  },
  "answers": [
    {
      "questionId": "q1",
      "selectedOptionIds": ["B"],
      "answeredAt": "2026-10-17T10:03:00Z"
    }
  ]
}
```

服务端根据 `correctOptionIds` 和 `selectedOptionIds` 计算对错；客户端不传可信的分数、正确率或 `isCorrect`。

成功响应示例：

```json
{
  "requestId": "req_01J...",
  "data": {
    "report": {
      "quizId": "quiz_7d9c...",
      "totalQuestions": 3,
      "correctCount": 2,
      "accuracy": 0.6667,
      "knowledgePoints": [
        {
          "name": "光合作用的条件",
          "correctCount": 0,
          "totalCount": 1,
          "needsReview": true
        }
      ],
      "summary": "本次对光合作用的主要能量来源掌握不足，建议复习光合作用的条件。",
      "reviewItems": [
        {
          "questionId": "q1",
          "reason": "未选中正确答案",
          "suggestion": "重点记忆光合作用需要光能。"
        }
      ]
    }
  },
  "error": null
}
```

### 7.6 错误码与 HTTP 状态

| HTTP 状态 | 错误码示例 | 含义/客户端处理 |
|---|---|---|
| 400 | `INVALID_REQUEST` | 请求 JSON 无法解析；提示检查请求 |
| 422 | `VALIDATION_ERROR` | 字段、题型、题目数、答案引用或文本长度不合法 |
| 429 | `RATE_LIMITED` | 本服务限流；展示稍后重试提示 |
| 502 | `AI_OUTPUT_INVALID`、`AI_EMPTY_OUTPUT` | 上游返回不可用/不符合预期的结构；答案保留，可重试 |
| 503 | `AI_PROVIDER_UNAVAILABLE` | 上游限速或暂不可用；可重试 |
| 504 | `AI_PROVIDER_TIMEOUT` | 模型调用超时；保留输入和答题记录 |
| 500 | `INTERNAL_ERROR` | 未预期错误；以 requestId 供客服/开发排查 |

FastAPI 的校验错误应统一转换为该响应格式。前端将错误码映射为用户可理解的提示，不展示内部异常。

## 8. 领域数据模型

本节定义业务对象和 API 级字段，不设计正式数据库表。

### 8.1 Quiz

| 字段 | 类型 | 说明 |
|---|---|---|
| `quizId` | string | 本次测验 ID；仅标识客户端会话，不代表服务端持久化 |
| `createdAt` | ISO-8601 string | 生成时间 |
| `sourceSummary` | string | 输入材料/主题摘要 |
| `questions` | `Question[]` | 本次题目 |

### 8.2 Question

| 字段 | 类型 | 说明 |
|---|---|---|
| `questionId` | string | Quiz 内唯一 |
| `type` | enum | `single_choice` / `multiple_choice` / `true_false` |
| `stem` | string | 题干 |
| `options` | `Option[]` | 选项；判断题使用统一约定的真/假选项 |
| `correctOptionIds` | `string[]` | 正确选项 ID；与 options 对应 |
| `explanation` | string | 答案讲解 |
| `knowledgePoint` | string | 关联知识点 |

### 8.3 AnswerRecord

| 字段 | 类型 | 说明 |
|---|---|---|
| `questionId` | string | 对应问题 |
| `selectedOptionIds` | `string[]` | 用户选项；可为空表示未答 |
| `answeredAt` | ISO-8601 string | 提交时间 |

是否正确由后端基于 Quiz 快照计算，不能信任客户端上送的派生结果。

### 8.4 Report

| 字段 | 类型 | 说明 |
|---|---|---|
| `quizId` | string | 对应测验 |
| `totalQuestions` | integer | 总题数 |
| `correctCount` | integer | 正确数 |
| `accuracy` | number | 0–1 之间的正确率 |
| `knowledgePoints` | array | 知识点维度统计 |
| `summary` | string | 知识总结 |
| `reviewItems` | array | 错题和复习建议 |

### 8.5 MVP 存储策略

1. 服务端不使用正式数据库；一次请求处理结束后不保留 quiz、报告或用户输入。
2. 前端仅在本地暂存当前测验和答题记录，供翻页、报告重试使用；用户清理本地状态后历史不可恢复。
3. 报告生成所需数据通过请求快照提交，因此不能用于防篡改、考试审计或跨设备历史。
4. 第二阶段如需恢复历史，优先选择 SQLite 作为本地开发/验证方案；正式用户和多实例服务需选定托管关系数据库后再建迁移脚本。
5. 不建议在 MVP 使用本地 JSON 文件存储运行时数据作为正式方案：并发写入、部署重启和多实例下容易造成数据不一致。

## 9. 页面与交互设计

### 9.1 页面列表

1. 首页：输入学习内容、选择题型/数量、开始生成。
2. 答题页：逐题作答、显示进度、提交后看答案和讲解。
3. 报告页：分数、正确率、知识点统计、复习建议和再次练习入口。

### 9.2 首页

- 提供主题/文本输入和示例占位提示。
- 提供 3–5 题范围内的题量选择，缺省 5 题；题型至少选择一种。
- 校验空输入和建议长度；生成期间禁用重复提交并显示加载状态。
- 失败时保留输入，展示可重试的错误信息。

### 9.3 答题页

- 一次展示一道题及进度，例如“第 2/5 题”。
- 单选题只允许一项，多选题允许多项，判断题用明确的正确/错误选项。
- 未选择时不允许提交；提交后立即展示正误、答案和解释。
- 已提交题目不可因返回页面而丢失；是否允许修改答案由产品后续确认，MVP 建议提交后锁定该题。

### 9.4 报告页

- 展示正确数、总题数和正确率。
- 展示薄弱知识点及与错题关联的复习建议。
- 生成报告失败时保留用户答案，可显式重试；不得展示虚构/空报告。
- 提供返回首页重新生成入口。

### 9.5 页面状态与体验原则

- 所有页面均覆盖 loading、success、empty 和 error 状态。
- 页面离开或小程序切后台时尽量保留当前本地会话。
- 题目讲解以短段落呈现；模型内容过长可在服务端设置输出限制，不由客户端任意截断答案。
- MVP 不设计复杂个人中心或视觉品牌方案，先验证交互闭环和内容质量。

## 10. 分阶段开发与验收

### Phase 0：环境与契约

**目标**

- 建立 Taro/React/TypeScript 前端和 FastAPI 后端项目。
- 建立 OpenAPI 契约、统一响应格式、配置样例、代码检查和测试命令。

**交付物**

- 本地前后端可运行，`.env.example` 不含真实密钥。
- `/api/v1/health` 可访问。
- API 请求/响应 DTO 与本设计一致。

**验收**

- 健康检查返回统一成功结构。
- 缺少必填环境变量时服务以明确错误启动，不静默填入假密钥。

### Phase 1：AI 题目生成

**目标**

- 完成 FastAPI `POST /quizzes`、DeepSeek 客户端、Prompt、解析与 Pydantic 校验。

**交付物**

- 可配置的模型调用、超时和错误码。
- 至少覆盖单选、多选、判断的离线响应样例和自动化测试。

**验收**

- 对 30 组代表性输入做回归：有效成功响应必须满足题量 3–5、题型合法、答案引用存在、选项 ID 不重复。
- 所有模型空响应、截断、JSON 解析失败和超时都返回明确错误，不产生成功形状的空题目。
- 人工抽检题目事实与讲解；建议以至少 95% 的题目/答案通过率作为 MVP 继续推进门槛，未达标先调整 Prompt 或切换模型评测。

### Phase 2：小程序首页与答题页

**目标**

- 使用 Mock 题目完成首页、输入校验、答题进度、题型交互和即时反馈。

**验收**

- 三类题型均能完成选择和提交。
- 页面切换后当前答题状态不丢失。
- 在微信开发者工具和至少一台真机验证核心流程。

### Phase 3：报告与接口接入

**目标**

- 实现报告页、API Client 和 `POST /api/v1/reports`。
- 报告统计由后端计算，模型只负责文字总结与建议。

**验收**

- 题目数、正确数、正确率和知识点统计可用测试答案精确复算。
- 模型报告不可用时显示明确错误且保留用户答案。
- 前端不包含 DeepSeek API Key 或其他服务端密钥。

### Phase 4：完整闭环联调

**目标**

- 打通真实模型生成、逐题反馈、报告生成、错误重试和 HTTPS 测试环境。

**验收**

- 从首页输入到报告页完成完整 E2E 流程。
- 覆盖空输入、非法题型、超长输入、上游超时/限流、无效模型 JSON。
- 关闭开发工具的域名校验绕过后，真机仍可访问配置的 HTTPS 域名。

### Phase 5：上线与增强

**目标**

- 完成平台账号/类目、域名备案、服务器域名、隐私说明、内容审核、日志和基础限流检查。
- 根据真实使用数据评估持久化、用户系统、文件解析及 RAG。

**上线检查**

- 微信服务器域名为已备案 HTTPS 域名，证书有效，配置的端口与请求 URL 一致。
- 生产密钥仅存后端；日志不包含密钥或不必要的完整用户输入。
- 设置文本长度、调用频率和超时限制；监控模型调用失败率和调用费用。
- 对生成内容的准确性、用户输入处理、平台类目和适用的中国大陆法律/平台要求完成上线前核查。

## 11. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 模型编造事实或答案错误 | 结构校验 + 代表性题库人工抽检；明确非权威用途；逐步建立质量回归集 |
| JSON Output 空响应或截断 | 检查空内容、设置合理 max_tokens、Pydantic 校验、受控重试后显式失败 |
| 模型 API 价格/模型版本变化 | 使用官方当前模型标识；按月或上线前复核官方价格与可用模型 |
| API Key 泄漏 | 仅服务端密钥配置；禁止进入客户端、日志和错误响应 |
| 恶意输入、Prompt 注入 | 把用户材料作为不可信内容；限制长度；系统提示固定；不执行用户内容中的指令 |
| 滥用调用造成费用增长 | 服务器端 IP/会话限流、题量和长度上限、超时、预算监控；不要信任客户端自报用户 ID |
| 无状态报告数据可被改动 | MVP 明确不防作弊；报告按客户端快照计算；正式考试需求须升级为服务端存储判分 |
| 微信正式环境网络失败 | 提前备案域名、配置 HTTPS 请求域名、检查证书/端口，并在真机关闭跳过校验验证 |
| 用户输入含个人信息 | 最小化采集，提示外部模型处理，避免收集身份信息；上线前核查隐私和合规要求 |
